Qomu App Anatomy

What actually runs on a Qomu, in what order, and which parts of the SDK each piece comes from. The worked example is qomu_apps/qomu_helloworldsw.

It's a FreeRTOS imageYour code is a CLI task. main() does bring-up, then starts the scheduler, which never returns.
USB lives in the FPGAThe S3 has no USB controller. The app loads a USB-serial core into the eFPGA to get a console.
It runs from SRAMThere's no internal flash. The bootloader copies your image from SPI flash to SRAM at 0x0.
Bootloader runs first, never linkedIt sits at SPI offset 0 and either reflashes the board or hands off to your image.
From reset to your code

Boot flow

The bootloader is a FreeRTOS app built the same way as yours. It loads the USB-serial gateware so it can talk to the programmer. Your app then has to load its own copy, because nothing in the fabric survives the handoff.

Flash map

The flash has no filesystem. It's a set of fixed regions defined in BSP/qomu/inc/flash_defines.h. Each image has a 4 KB metadata sector that the bootloader checks before loading it.

Memory at runtime

The linker's rom region starts at address 0, but it's SRAM that the bootloader fills. That puts your hard size limit at about 156 KB of code and read-only data, well under the 440 KB flash slot.

The console stack

Fw_global_config.h sets DEBUG_UART to UART_ID_USBSERIAL. The HAL UART layer then works as a switch: it sends "UART" traffic to the FPGA's USB core, not to a physical UART pin.

What comes from the rest of the SDK

Platform

  • HAL/startup: vector table and C runtime startup, which calls SystemInit() and then main()
  • HAL/src: UART dispatch, GPIO, clocks, pads
  • BSP/qomu/src: qomu_hardwaresetup(), which applies your pwrcfg and pad tables
  • FreeRTOS: the kernel and the Cortex-M4F port

Libraries and gateware

  • Libraries/cli: the menu engine
  • Libraries/Utils: dbg_uart, the console print helpers
  • Libraries/FPGA: load_fpga()
  • Libraries/Power: the S3x_Clk_* and power-island framework
  • s3-gateware: the M4-side USB-serial driver

The bootloader has its own near-copy of qomu_hardwaresetup.c, which also sets up SPI and GPIO interrupts. Your app links the BSP version, not the bootloader's.

Before you change things

Gotchas

Keep FPGA, clocks and pins in sync

If you swap the bitstream, recheck s3x_pwrcfg.c (fabric clocks) and pincfg_table.c (pads routed to the fabric). If they don't match, USB stops enumerating and you get no error.

Breaking USB loses the console

Your console depends on the gateware. If load_fpga() or the USB init fails, there's no output at all. Blink an LED early in main(), or keep an SWD probe handy.

SRAM is the size limit

The image has to fit the ~156 KB rom region, including the embedded bitstream. The 440 KB flash slot doesn't help past that.

Recovering a stuck board

Press reset, then the user button within 5 s, to enter download mode. If the bootloader itself is damaged, use qomu_loadflash over SWD. Factory images are in qomu_apps/qomu-initial-binaries.
