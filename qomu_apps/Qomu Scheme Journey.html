Qomu Scheme: from question to REPL

How a Scheme interpreter went from "do you think we can?" to a working prompt on the Qomu's USB-serial console in one morning: what we built, how it fits into the SDK, and every bug we hit on the way to the first >. Part two follows a paste problem down into the eFPGA: the USB core rebuilt from source with the open toolchain, three gateware bugs, RX flow control, and measurements that traced the last two missing bytes to screen. Part three makes the interpreter 3.3× faster and tidies up the gateware until every path meets timing. Part four tries 72 MHz, parks it, and keeps three gateware fixes it uncovered: the suite now runs over USB in 32.8 s instead of 52.9. Part five gives programs somewhere to live: named files in the spare megabyte of SPI flash, a boot file that runs at power-up, and a boot log that stops a bad one from locking you out.

What runs where

Architecture

The core knows nothing about the board. Everything Qomu-specific lives in scheme_task.c and scheme_port.h, so the same scheme.c runs on a laptop for testing.

scheme.c

Interpreter design

Objects

  • 12-byte cells on the M4: type, mark, 16-bit aux, 8-byte union.
  • 31-bit integers are immediate (low bit set) and never allocate.
  • Larger integers are boxed int64, so register addresses like #xE000E010 work; overflow falls back to float.
  • Floats are single precision, to use the M4F's FPU.
  • String and vector bodies come from pvPortMalloc and are freed by the GC.

Memory

  • Mark/sweep over a caller-supplied cell array.
  • Every new cell is pushed onto a GC root stack, so C temporaries are always safe; each eval frame trims the stack when it finishes.
  • Marking uses a bounded explicit stack with an overflow rescan, so deep data can't blow the C stack.
  • Verified by running the suite with a GC on every allocation and freed cells poisoned.

Evaluator

  • Walks the source tree directly, with tail calls through if/cond/case/and/or/let*/named let/bodies.
  • Global variables live in the symbol; local frames are association lists.
  • Macro expansions are memoized by rewriting the call site.
  • Non-tail recursion is capped by a C-stack budget (17 KB) and the root stack (1,024 entries); both come to about 150 levels.

Errors and the console

  • Errors longjmp back to the REPL, with the offending value printed and truncated.
  • Ctrl-C is polled every 512 evals; other keys typed meanwhile are kept as typeahead.
  • No libc printf: integers and floats are formatted by our own code, since newlib-nano drops %lld and %f.

Language: quote quasiquote lambda define set! if cond (with =>) case and or when unless let let* letrec begin define-macro, plus do while dotimes delay as library macros. Not supported: continuations, rationals and ports.

qomu.ld · SRAM, to scale

Memory layout change

The first link overflowed rom, the region that holds code plus the initial values for .data. That included the 76 KB FPGA bitstream, which was a writable array, so it occupied both rom and RAM. Making it const freed the RAM copy, and that RAM paid for moving the boundary up 32 KB.

Between "it compiles" and ">"

What broke, and why

config.mk:145 — first argument to 'word' must be greater than 0 build host

GNU Make 4.4 (Trixie) now passes exported variables to $(shell …) commands. export PROJ_DIR=$(shell pwd) is evaluated every time it's used and comes out empty, which leaves PROJ_NAME empty. Bookworm's Make 4.3 didn't do this.

Fix: export PROJ_DIR:=$(shell pwd), so it's evaluated once. Every other app's config.mk has the same line and will hit the same error.

region 'rom' overflowed by 424 bytes linker

About 30 KB of interpreter pushed the image (160,168 bytes) past the 156 KB code region. The _fstat/_kill warnings next to it are harmless newlib stubs.

Fix: make axFPGABitStream const (cast where it's passed to load_fpga(), which reads it with plain CPU loads), and move the rom/ram boundary from 0x27000 to 0x2F000.

Enumerates, but the console is silent firmware

HAL_usbserial_putc() busy-waits for room in the TX FIFO, and the FIFO only drains while the host has the port open. At boot nobody is reading, so the banner filled the FIFO and the task never reached the code that reads keys. LED checkpoints pinned it down: green stayed on.

Fix: q_putc waits up to 100 ms, then drops output until the FIFO drains. The banner prints after the first keypress.

Error: recursion too deep — printing the banner interpreter

The stack-depth check records a base address the first time Scheme code runs. On the board that's the prelude, deep inside scm_init(). The banner was printed from higher up the stack, the depth came out negative, and (size_t) wrapped it to a huge value. The host tests never printed from above the base.

Fix: a signed comparison, and keep the shallowest entry point as the base. A host test now reproduces the board's startup.

A fix that didn't reach the checkout workflow

The file-copy tool briefly wrote the previous scheme.c; git status was clean and the size hadn't changed. Caught because Andrey checked.

Fix: applied in place and compared byte for byte with the tested version. Every write is now verified in the checkout.

Junk at the first prompt: ##############QScV qp host tty

The boot banner from main() is echoed back by the Linux tty before screen switches the port to raw mode, and the reader parses it as input. Harmless.

Fixed (23 Nov): after the first key the firmware waits 150 ms, then discards everything received, that key included, before printing its banner.

Part two · Sunday afternoon to Monday evening

The paste problem

Pasting tests.scm in one go garbled it; single lines were fine. The firmware fixes came first, and none of them was enough. A measurement then showed why: one read of an FPGA register costs 112 CPU cycles. A paste arrives faster than the M4 can empty the gateware's 512-byte receive FIFO, and the stock usb2serial core has no way to tell the host to wait. Fixing that meant changing the gateware, and the only bitstream we had came from QuickLogic's proprietary SpDE tools. So we ported the core to the open toolchain.

qomu_scheme/gateware

The open-toolchain port

The starting point was usb2serial from s3-gateware (commit 2f8fed6), the core behind helloworld's SpDE bitstream. SpDE-specific pieces were replaced with what Yosys and VPR understand, and the build emits the same C array axFPGABitStream that load_fpga() already loads, so the firmware side barely changed.

Toolchain

  • ql_symbiflow v1.3.0 in an Ubuntu 20.04 image, symbiflow-qomu, built from gateware/docker/Dockerfile.
  • Miniconda with Python 3.7, and exact versions of Yosys, its plugins and VTR pinned.
  • Device ql-eos-s3_wlcsp, package WR42. Runs on Apple silicon under amd64 emulation.

RTL changes

  • The SpDE pad cell became a plain tristate assign.
  • The SpDE-generated RAM and FIFO cores were rewritten as wrappers around the toolchain's primitives.
  • The clock divider and switch were removed: 48 MHz comes straight from Sys_Clk1.
  • A missing module was recreated, a duplicate removed, and a few simulation races fixed.

Pins and pads

  • qomu.pcf: D+ on ball E4, D− on F3, pull-up control on E2, taken from the Qomu schematic.
  • iomux2c.py turns the toolchain's pad script into qomu_fpga_pads_init(), which main() calls before load_fpga().
  • Inputs from the fabric need the pad's receive-enable bit; the script sets it and raises the drive to 4 mA.
Between "it routes" and ">"

What broke, part two

Paste loss with (rx-dropped) at 0 gateware

The typeahead and polling fixes helped, but input still went missing while the firmware's own buffers never overflowed. The bytes were lost in the gateware FIFO, which the M4 drains at two 112-cycle register reads per byte.

Fix: RX flow control in the gateware, described below.

The official installer produced no yosys toolchain

It installs the latest Miniconda, whose Python doesn't match the 3.7 packages, and it doesn't check for errors. Smaller snags followed: the Docker credential helper wasn't on the PATH, VPR needed libtbb.so.2, and the simulation library lacked a model for the clock buffer.

Fix: our own Dockerfile with every package pinned, libtbb2 installed, and a stand-in clock-buffer model for simulation.

Not enumerating: error -71 gateware

The pull-up worked and the FPGA configured, but the host never got a usable answer. Pad receive-enable, simulation race fixes, a timing constraints file, and a rewrite of the receiver's line-state logic each changed nothing. Counters read out over LEDs showed valid packets arriving and replies leaving, which put the fault in the transmitter. The timing report agreed: its 32-bit state compare needed ~50 ns per 48 MHz clock.

Fix: the transmitter runs on the 12 MHz clock, one bit per clock. Two follow-ups: a byte load now takes priority over the bit shift in the same cycle, and the first CRC byte includes the last data bit. The only remaining timing violation is in a debug counter.

Enumerates, but no input and no output gateware

Upstream bug: reading a received byte should remove it from the FIFO, but the check compared a word address with a byte address and never matched. Separately, with the open toolchain the hard FIFO block didn't move data; we didn't pin down why. The RAM block, by contrast, was proven: the USB packet buffers use it, and the enumeration descriptors pass through it.

Fix: a one-line address fix, and both FIFOs rebuilt on the RAM block, with their own read and write pointers and the same flag values, so firmware and HAL are unchanged. The simulation now pushes data both ways.

The first read of endpoint 1 is empty upstream

Whenever its FIFO is empty, the bridge marks endpoint 1's packet as complete, so after reset the first IN request gets a zero-length packet. A real host simply polls again.

Fix: none needed; the testbench expects the empty packet first.

Status lines came back as input host tty

Diagnostic lines printed while waiting for the first key were echoed back by the Linux tty, still in its default cooked mode, and the reader took them as typing.

Fix: nothing is sent before the first key; the lines stay behind SCHEME_WAIT_STATUS.

The paste still garbled gateware

With the new core working, a big paste still overflowed the 512-byte FIFO: the host delivers data faster than the M4 drains it.

Fix: the bridge pulls a byte from the 32-byte packet buffer only when the FIFO has room for four. When the FIFO fills, draining pauses, the packet waits in the buffer, and the USB core answers the host's next packet with NAK until there's room. The host retries automatically.

unbound variable: genm screen

Two bytes go missing at offsets 5118–5119 on every interactive paste. Counters show they never reach the gateware; written straight to the port, the same file arrives complete.

Testing one link at a time cleared the terminal app, ssh and the Pi's pty. screen pasting the file from its own buffer delivered it intact; typed input relayed through screen did not. Typed input waits in a 4 KB per-window buffer while the write to the port is stalled, and the bytes go missing around the point where it fills. screen's bug tracker has the same report: readbuf works, a terminal paste corrupts.

Fix: use picocom (or tio) for interactive work: full-file pastes arrive complete. With screen, load files with readbuf and paste, or with tools/paste_test.py.

scheme.c · scheme_task.c

What made it faster

Fast primitive path

  • + - * < > = <= >= with two small integers, and car cdr cons null? pair? not eq? zero?, are computed straight from C variables.
  • Primitives are recognized by function pointer, so the cell layout is unchanged.
  • Floats, overflow and wrong types fall back to the generic call, so results and error messages stay identical.

Inline leaves

  • Numbers, variables and self-evaluating data are handled at the call site, without the full eval entry, stack check and polling.
  • Looked-up values still go on the GC root stack: a later argument could set! the variable they came from.

Cheaper frames

  • A call made by the evaluator reuses its freshly built argument list as the frame's binding list: one new cell per parameter instead of two.
  • Lists that may be shared, from apply or macro arguments (source code), are never modified.

Build and stack check

  • SCM_OPTIMIZE_SPEED in scheme_port.h compiles scheme.c with -O2 through a pragma; the rest of the firmware stays at -Os.
  • The recursion-depth check is one comparison against a precomputed limit.

Batched receive interrupt

  • The FIFO's pop flag guarantees a minimum fill level (1, 2, 4 … 512 bytes). The interrupt reads the flags once, then pops that many bytes with one read each.
  • Before, the HAL read the flags twice per byte, then the data: 7 µs per byte instead of 2.3.

Part four

What broke, part four

The power policy resets the CPU clock firmware

Raising C10's start value isn't enough: at boot the app applies power policy 1, whose table sets C10 to 48 MHz. With a 72 MHz oscillator that would have given 36.

Fix: the policy entries follow SCHEME_CPU_MHZ too.

Clock requests round the wrong way firmware

The clock driver computes its divider as source / rate, rounding down. The HAL's request for 48 MHz from a 72 MHz source gives divider 1: 72 MHz, silently.

Fix: main.c sets C21 explicitly after the HAL's init.

A falling-edge flip-flop costs a logic cell toolchain

The fabric's logic cell has a clock-polarity bit, but the toolchain's mapping doesn't use it; it inverts the clock through a separate cell. VPR treats the generated clock as ideal, so its timing report can't show the resulting skew.

Lesson: read the netlist (build/*.eblif), not just the timing summary. VPR names clocks after the net driving their clock buffer, which pack.log lists.

The transmitter started from the wrong line state upstream

Upstream let the NRZI encoder run on idle data and relied on the 7-bit wait to leave the line state at J. Starting sooner sent an inverted sync pattern, and the waveform showed it at once.

Fix: hold J while the output is off.

A synchronizer that read its metastable stage upstream

strobe.v XORed the first and second synchronizer flip-flops; the commented-out original used the second and third. When the flag changed in the first flop's setup window, an event arrived twice (a duplicated byte) or not at all (a lost byte or packet end). Whether that happens depends on the phase between two clocks from the same oscillator and on routing, so it changed from build to build.

Fix: synchronized stages only, at a cost of one 12 MHz clock.

Placement moved a receiver path over the limit gateware

Back at 48 MHz, a slightly changed netlist routed the packet-boundary detector to 22.6 ns against 20.8: 9.8 ns of routing from a high-fan-out register, then three logic levels.

Fix: a private copy of that register and precomputed history matches; 20.5 ns.

A failed compile installed the old bitstream build script

build.sh ran install after a failed compile, from the previous header. The first fix then rejected an up-to-date build that make had rightly skipped.

Fix: install only if the bitstream is newer than every source and constraint file.

Part five · Friday morning

Flash storage

Until now everything typed into the REPL was gone at power-off. The Qomu's 2 MB SPI flash holds the bootloader, its metadata, the gateware and the M4 app, all below 1 MB; the BSP map lists the top megabyte, 0x100000–0x1FFFFF, as unused. That megabyte is now a small file store: fifteen 64 KB slots, each a header page and up to 65,280 bytes of Scheme source. The rule from the start was to touch nothing below 1 MB, and every flash access is range-checked twice to enforce it.

Of three layouts (a raw region, a log-structured store, named slots) Andrey picked named slots: "simple, direct and sufficient". A save writes the new copy to a free slot, reads it back, and only then writes its header; the old copy is deleted after that. A sequence number in the header settles the instant between those two writes, so a power cut leaves either version but never neither. The logic was built against a simulated NOR chip on the host first, with a cut injected after every page write.

Part five

How the store works

Slots. Slot n starts at 0x100000 + n × 64 KB. Page 0 is the header: magic QSF1, length, CRC-32, sequence number, name. The text starts at page 1. Writing streams a page at a time and erases each 4 KB sector just before its first page, so a short file costs one erase. Deleting programs the magic to zero; NOR bits only go from 1 to 0, so no erase is needed.

Reading. load checks the CRC, then hands a page-at-a-time reader to a new scm_eval_stream() in the interpreter core. A file's size isn't limited by RAM, and files can load other files.

The boot log is the first sector of the 16th slot, one byte per power-up that runs boot: 0F when it starts, 00 when it returns (finished, an error, or Ctrl-C). If the last two records are both 0F, those power-ups never got back to the firmware, and boot is skipped with a note under the banner. Saving or deleting boot, or (boot-ok) at the REPL, re-arms it. A program meant to run forever calls (boot-ok) once it's up, so unplugging it doesn't count against it. The sector is erased once every 4,096 records.

Part five

What broke, part five

The page writer advances twice upstream

spiflash_write() adds each chunk to its position inside the loop body and again in the for statement, so any write longer than one chunk skips data and stops early. It also splits a partial page into halves.

Workaround: exactly one whole, page-aligned 256-byte write per call, where the loop runs once.

Block erases ignore the low address bits driver

spiflash_erase() picks a 64 KB or 32 KB block erase when the length allows. The chip erases the aligned block containing the address, so an unaligned start would erase below it.

Rule: one 4 KB sector per call, aligned and range-checked.

Reads move whole words driver

The read path always uses DMA, which rounds the length up to a multiple of 4.

Rule: word-aligned buffers and lengths rounded up to 4; the store never reads into a buffer that couldn't take the extra bytes.

An error mid-paste fed the REPL ours

On the host, a file over the size limit raised its error at the overflow, and the rest of the paste went to the REPL as code.

Fix: keep reading to the terminator, then report.

The banner counted garbage ours

Free cells read 3031, then 2885, then 2604 across power-ups: the banner counted before collecting what boot had left behind.

Fix: (gc) before the banner.

  5. More interpreter speed: profile real programs; cache global lookups; fewer cells for let and closures.
  6. Request our own USB product ID. QuickLogic's 1d50:6140/6141 were never registered for it: Openmoko's registry assigns them to Osmocom's osmo-ASF4-DFU bootloader and sysmoOCTSIM reader (TinyFPGA, whose USB core ours descends from, has 6130). Open projects qualify; you apply with a pull request to openmoko/openmoko-usb-oui, then change usbpid in main.c.
