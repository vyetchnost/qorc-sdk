Qomu Scheme: from question to REPL

How a Scheme interpreter went from "do you think we can?" to a working prompt on the Qomu's USB-serial console in one morning: what we built, how it fits into the SDK, and every bug we hit on the way to the first >.

What runs where

Architecture

The core knows nothing about the board. Everything Qomu-specific lives in scheme_task.c and scheme_port.h, so the same scheme.c runs on a laptop for testing.

scheme.c

Interpreter design

Objects

  • 12-byte cells on the M4: type, mark, 16-bit aux, 8-byte union.
  • 31-bit integers are immediate (low bit set) and never allocate.
  • Larger integers are boxed int64, so register addresses like #xE000E010 work; overflow falls back to float.
  • Floats are single precision, to use the M4F's FPU.
  • String and vector bodies come from pvPortMalloc and are freed by the GC.

Memory

  • Mark/sweep over a caller-supplied cell array.
  • Every new cell is pushed onto a GC root stack, so C temporaries are always safe; each eval frame trims the stack when it finishes.
  • Marking uses a bounded explicit stack with an overflow rescan, so deep data can't blow the C stack.
  • Verified by running the suite with a GC on every allocation and freed cells poisoned.

Evaluator

  • Walks the source tree directly, with tail calls through if/cond/case/and/or/let*/named let/bodies.
  • Global variables live in the symbol; local frames are association lists.
  • Macro expansions are memoized by rewriting the call site.
  • Non-tail recursion is capped by a C-stack budget (17 KB) and the root stack (1,024 entries); both come to about 150 levels.

Errors and the console

  • Errors longjmp back to the REPL, with the offending value printed and truncated.
  • Ctrl-C is polled every 512 evals; other keys typed meanwhile are kept as typeahead.
  • No libc printf: integers and floats are formatted by our own code, since newlib-nano drops %lld and %f.

Language: quote quasiquote lambda define set! if cond (with =>) case and or when unless let let* letrec begin define-macro, plus do while dotimes delay as library macros. Not supported: continuations, rationals and ports.

qomu.ld · SRAM, to scale

Memory layout change

The first link overflowed rom, the region that holds code plus the initial values for .data. That included the 76 KB FPGA bitstream, which was a writable array, so it occupied both rom and RAM. Making it const freed the RAM copy, and that RAM paid for moving the boundary up 32 KB.

rom156K · 0x00000
ram242K · 0x20027000 (bitstream copy 76K here)
spiram · HWA · shm114K
qomu_scheme
rom188K · 0x00000
ram210K · 0x2002F000 (no bitstream copy)
spiram · HWA · shm114K
0x000000x200000x400000x600000x80000

This is safe because the bootloader accepts M4 images up to 440 KB, and it stages the first 64 KB near the top of SRAM, above everything here. ram still ends at 0x20063800, so the main stack didn't move. Net RAM change: about 44 KB gained.

Between "it compiles" and ">"

What broke, and why

config.mk:145 — first argument to 'word' must be greater than 0 build host

GNU Make 4.4 (Trixie) now passes exported variables to $(shell …) commands. export PROJ_DIR=$(shell pwd) is evaluated every time it's used and comes out empty, which leaves PROJ_NAME empty. Bookworm's Make 4.3 didn't do this.

Fix: export PROJ_DIR:=$(shell pwd), so it's evaluated once. Every other app's config.mk has the same line and will hit the same error.

region 'rom' overflowed by 424 bytes linker

About 30 KB of interpreter pushed the image (160,168 bytes) past the 156 KB code region. The _fstat/_kill warnings next to it are harmless newlib stubs.

Fix: make axFPGABitStream const (cast where it's passed to load_fpga(), which reads it with plain CPU loads), and move the rom/ram boundary from 0x27000 to 0x2F000.

Enumerates, but the console is silent firmware

HAL_usbserial_putc() busy-waits for room in the TX FIFO, and the FIFO only drains while the host has the port open. At boot nobody is reading, so the banner filled the FIFO and the task never reached the code that reads keys. LED checkpoints pinned it down: green stayed on.

Fix: q_putc waits up to 100 ms, then drops output until the FIFO drains. The banner prints after the first keypress.

Error: recursion too deep — printing the banner interpreter

The stack-depth check records a base address the first time Scheme code runs. On the board that's the prelude, deep inside scm_init(). The banner was printed from higher up the stack, the depth came out negative, and (size_t) wrapped it to a huge value. The host tests never printed from above the base.

Fix: a signed comparison, and keep the shallowest entry point as the base. A host test now reproduces the board's startup.

A fix that didn't reach the checkout workflow

The file-copy tool briefly wrote the previous scheme.c; git status was clean and the size hadn't changed. Caught because Andrey checked.

Fix: applied in place and compared byte for byte with the tested version. Every write is now verified in the checkout.

Junk at the first prompt: ##############QScV qp host tty

The boot banner from main() is echoed back by the Linux tty before screen switches the port to raw mode, and the reader parses it as input. Harmless.

Planned: discard input that arrives before the first real keypress, or drop the boot banner.

Build and flash

# Mac (reference checkout, edited by Claude)
git add -u qomu_apps/qomu_scheme && git commit -m "…" && git push

# Pi 4 build host
git pull && cd qomu_apps/qomu_scheme/GCC_Project && make
cd ../../../TinyFPGA-Programmer-Application
python3 ./tinyfpga-programmer-gui.py --port /dev/ttyACM0 \
    --m4app ../qomu_apps/qomu_scheme/GCC_Project/output/qomu_scheme.bin --mode m4

# replug (app enumerates as 1d50:6141), then
screen /dev/ttyACM0        # press Enter for the banner and "> "

Flashing only writes the m4app region. To go back, flash qomu_apps/qomu-initial-binaries/qomu_helloworldsw.bin the same way.

Queued

Next steps

  1. do (and so blink) should return nothing instead of #f.
  2. Discard input that arrives before the first keypress (the echoed boot-banner junk).
  3. Multi-line pastes lose characters while the REPL is busy: the 32-byte typeahead buffer drops anything beyond it. Stop reading when the buffer is full, so the bytes wait in the FPGA FIFO, and make the buffer bigger.
  4. Remove the LED checkpoints, or keep them behind a build flag.
  5. Speed: cache global lookups, allocate fewer cells per call, -O2 for scheme.c, and maybe C10 at 72 MHz once the USB core is confirmed unaffected.
  6. Bigger ideas: save and load Scheme source in the spare SPI flash; primitives for registers in your own FPGA logic.
